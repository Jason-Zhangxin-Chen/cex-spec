01 · 系统概览

系统概览

多活高可用 CEX 交易系统面向不同区域提供服务：用户请求由云厂商 GTM 依据流量路由策略调度到不同数据中心的 CEX 集群，跨 DC < 100km Raft HA，同数据中心内服务本地 HA 复制。用户面流量（客户端与 OpenAPI）经 GTM DNS 层的 CDN、DDOS 防护与 WAF 过滤后进入 LB 集群（无状态，注册到 GTM）；控制面（八个运营 UI 与 MPC 审批 App）经 VPN 通道一、监控与治理面（集群监控 / 治理 UI）经 VPN 通道二接入。nginx 网关集群负责流量控制、业务请求路由与限流，将请求直接转发至服务集群。服务集群分四类：**内核服务（有状态）**（22 项：实时热备集群虚拟组（预交易集群（资金冻结预留，冻结与订单受理原子化）、OMS & 撮合引擎集群（现货/永续/期权/预测四条产品线）、风控监测引擎集群（标记价/成交/资金费/转账事件驱动）与风控治理服务集群（强平/保险/ADL，含强平状态机）、行情引擎集群（按 Symbol 分片）——均主 + 多从，DC 内仲裁同步日志复制、跨 DC 半同步日志复制）、弱状态服务集群（清算集群（持仓簿/保证金核算/现货内部结算）与结算集群（衍生品结算：定期资金费率、到期期权交割）、充提币服务集群（提现请求、充值扫链、地址白名单、签名编排）、C2C/P2P 交易服务集群、用户资产核算服务集群、AI 交易集群（AI 推理 · 账户委托交易）与指数价格服务集群——快照 + 日志重放 · 事件序号保证幂等恢复）、钱包服务集群（内含钱包&钱包风控、MPC 签名网关、MPC Actor、KYT、KMS/HSM 密钥管理子系统）与数据写入、快照与投影层（账本集群（账本数据单一事实源）、持仓/保证金集群（持仓/保证金数据单一事实源）、数据归档集群（历史数据归档，写入对象存储）与 ES 数据集群（订单/成交/流水查询、应用日志聚合）——事件序号保证幂等）、**边缘服务**（9 项无状态：用户管理集群、鉴权集群、交易调度集群（按账户 ID 分片调度至主预交易节点；预交易集群向其注册主从 IP，双 DC 均可调度）、用户消息集群、KYC 集群、活动服务集群、Open API Key 集群与数据读取管线子组（行情发布/订阅集群 + 数据读取集群））、**控制面服务**（11 项：运营配置（含风控引擎 · 费率）、持仓锁定、红包、IEO、空投、优惠券、审计日志服务、监管报表服务、定时调度服务、资金对账服务与配置中心）、**监控与治理面**（2 项：监控与治理集群——指标 / 健康监控，主从故障切换由共识算法自动完成；撮合回放服务集群——基于列式数据 Raft 集群回放撮合）；无状态 / 有状态以配色区分；Aeron Raft 集群（分布式消息总线）用于服务集群内部服务间通信。数据层集群：Aeron Raft 集群、Redpanda Raft 集群（高性能 Kafka 分布式消息队列）、Redis 集群、行情数据中心、列式数据 Raft 集群（行情回归测试）、SQL Raft 集群（上→下投影 · 下→上恢复）、对象存储 Raft 集群与时间序列 Raft 集群。外部系统连接器：公链 RPC、KYT 提供商、第三方 KYC 提供商、第三方钱包代理、法币通道代理与指数价格数据源。

02 · 账户模型

账户模型

CEX 账户的数据模型是分层且多维的：它不存单一的「余额」数字，而是按钱包类型 × 资产 × 余额状态（可用、锁定、保证金等）拆分持仓。这一结构是同时支撑现货、杠杆、衍生品与法币业务的必要前提——该模型回答的不只是「用户有多少钱」，而是「现在能用多少、已经承诺了多少」，并同时覆盖每个产品线与每种资产。

24 个模型对象
3 条连接
3 层结构
7 种钱包
6 个存储字段 + 2 个派生值

层级结构：账户 → 钱包 → 资产余额

单个用户账户（以唯一 accountId 标识）不是一个整体资金池，而是多个子账户 / 钱包的容器，每个钱包承担不同的职责。

层级实体说明关键字段（示例）
1. AccountAccount根身份。accountId、accountType（SPOT、MARGIN、FUTURES…）、updateTime
2. WalletWallet / 子账户按产品线隔离资金（现货、全仓杠杆、USDⓈ-M 合约、COIN-M 合约、资金、理财）。walletType、walletBalance（汇总）
3. Asset BalanceAssetBalance特定钱包内的单资产持仓记录。asset（BTC、ETH、USDT）、free、locked、borrowed、interest
为什么分离？交易所按产品线隔离钱包（现货 vs 合约）是出于风控与系统架构考量——合约引擎的故障或异常不应直接影响现货钱包。

单一资产的多维余额

对特定钱包内的任一资产（如 USDT），模型存储多个余额维度而非单一数字：

free / availableBalance—— 立即可用

立即可用于新订单、提现或划转的数量。Binance API 中现货为 free，合约 / 杠杆为 availableBalance。

可用 = 钱包总余额 − 锁定 − 保证金抵押 − 未实现亏损（衍生品）

locked / reserved—— 已预留

已预留、因投入他处而不可用的资金：挂单（订单簿上未成交部分）、保证金抵押（支撑杠杆持仓）、理财 / 质押（未赎回的收益产品）。Lighter 的 AccountAsset 显式命名为 locked_balance。

totalWalletBalance / balance—— 毛持有量

该钱包内资产的毛持有量，未扣锁定、未加减未实现盈亏。Binance 组合保证金 API 将 totalWalletBalance 定义为某资产跨特定钱包类型的汇总值。

marginBalance—— 有效权益（衍生品 / 杠杆）

杠杆交易中的动态指标，代表支撑持仓的有效权益。Lighter 的 AccountAsset 中 margin_balance 与 balance、locked_balance 分列；全仓杠杆进一步扩展 crossMarginFree / crossMarginLocked / crossMarginBorrowed / crossMarginInterest。

保证金余额（合约）= 钱包余额 + 未实现盈亏

borrowed & interest—— 债务（杠杆专有）

杠杆交易显式跟踪债务：borrowed 为欠交易所 / 贷方的数量；interest 为借款累计利息。Binance 的 MarginBalance GraphQL 类型在 AssetBalance 之上扩展这两个字段。

unrealizedPNL—— 未实现盈亏（衍生品专有）

衍生品钱包（USDⓈ-M 与 COIN-M）的资产记录含 umUnrealizedPNL 与 cmUnrealizedPNL，直接影响 marginBalance。

法币（USD）如何融入

法币（如 USD）在系统里就是另一种资产：用户现货或资金钱包中的美元持仓即 asset = "USD" 的 AssetBalance，与加密资产共享同样的维度（free、locked）。唯一区别在出入金通道（银行转账 vs 区块链），核心余额数据模型不变。

概念 Schema

Account - account_id (PK) - user_id - account_type (SPOT, MARGIN, FUTURES, etc.) - status - update_time AssetBalance (PK: account_id + wallet_type + asset) - account_id (FK) - wallet_type (e.g., SPOT, CROSS_MARGIN, UM_FUTURES) - asset (e.g., BTC, USDT, USD) - total_balance // 钱包毛余额 - available_balance // 可用于新订单 / 提现 - locked_balance // 挂单、抵押预留 - borrowed // 杠杆负债（不适用时为 0） - interest // 累计杠杆利息 - unrealized_pnl // 衍生品钱包专有 - margin_balance // 钱包余额 + 未实现盈亏（衍生品）
关键结论：该模型回答的不只是「用户有多少钱」，而是「现在能用多少、已经承诺了多少」——横跨每个产品线与每种资产。

  • AssetBalance 是数据库行，不是事实源。真实 CEX 中权威记录是追加式复式记账账本（LedgerEntry { account_id, wallet_type, asset, delta, ref_id: OrderId|TradeId|TransferId, seq }），本结构是从账本重建的物化快照。账本让对账与审计成为可能；快照则为热路径提供 O(1) 读取。
  • available 是唯一允许为负的字段，且仅限杠杆钱包——这是保证金追缴信号；其余字段均由 validate() 守护。
  • Option<Decimal> vs Decimal::ZERO：选择平铺零值 + validate() 在错误钱包类型上拒绝——与交易所的存储方式一致（无 NULL 表、SUM 开销低），同时在边界上用不变量找回类型安全。
  • 持久化：在 feature flag 下为 AssetBalance derive sqlx::FromRow，表主键 PRIMARY KEY (account_id, wallet_type, asset)；跨钱包聚合查询需要 (account_id, asset) 覆盖索引。
  • 使用 rust_decimal（features = ["serde-with-str"]）：金额以 JSON 字符串往返，绝不经过 f64。

关系汇总

边基数机制为什么
Account → Wallet1 : NHashMap<WalletType, Wallet>按产品线隔离风险（合约引擎故障 ≠ 现货损失）
Wallet → AssetBalance1 : NHashMap<Asset, AssetBalance>热路径 O(1) 查找（acct.wallet(Spot)?.balance(&BTC)）
AssetBalance叶子行PK = (account_id, wallet_type, asset)每（账户、产品、资产）三元组唯一
WalletType封闭枚举IsolatedMargin(u32) 携带交易对 id逐仓杠杆需要每个交易对一个虚拟钱包
经验法则：如果想在这棵树里把资金从一个盒子移到另一个盒子，那是复式记账账本的转账，而不是对单个 AssetBalance 的修改——上面的树只是快照，账本才是事实源。

导入

导入按 ID 更新（upsert），重复运行是更新模型而不是重复创建。命名空间 cex-trading 便于按来源清理。

# 项目目录：/home/jason/designs/cex_icepanel export ICEPANEL_API_KEY=... # 列出你的组织与 landscape ID python3 import_to_icepanel.py --list-orgs # 导入 / 更新模型（Model-as-code） python3 import_to_icepanel.py <landscape-id> # 或直接调用 API： curl -X POST "https://api.icepanel.io/v1/landscapes/$ID/versions/latest/import" \ -H "X-API-Key: $ICEPANEL_API_KEY" \ -H "Content-Type: application/json" \ --data-binary @icepanel-landscape.json
